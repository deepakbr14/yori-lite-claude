# Safe Docs-to-Sheets staging and migration

This procedure is an optional, explicitly scoped operation, not part of ordinary startup. Do not migrate the original personal Yori. Existing config discovery, selected folder, permissions and representation remain unchanged. Installation alone never edits a Cortex or pointer.

1. Resolve the actual config and selected Docs Cortex. Save an exact copy of the config's chosen description/body representation, IDs and revision/metadata evidence for rollback. Keep originals in place. Verify the current user can read every source; permission failures are not empty folders.
2. Using Claude's actual Drive and Docs connectors, enumerate Self, People, Knowledge, History, addenda, corrections and all pages. Read full native content including tabs, tables, sections and attribution; do not use snippets or blank exports. Export a local JSON snapshot with `cortex_folder_id`, `complete:true`, `exported_at` from a reliable clock, and `documents`. Each document includes `id`, `kind`, `title`, complete readable `content`, `source_revision` (explicit "unavailable" if absent), `complete:true`, `verified_in_scope:true`, optional contributor/attribution/event times, URL and `raw_document` if useful. Preserve all original text; do not summarize or silently discard structure. Missing completeness means migration is blocked for that source.
3. Optional offline utility: `python3 scripts/graph_cortex.py migrate snapshot.json --output staged-graph.json`. It reads the connector-exported snapshot, preserves source IDs as node IDs (History source IDs as event IDs), keeps complete text and provenance, makes deterministic retry IDs, and emits full rows/manifests without network access. It never writes Google or changes config. It deliberately generates NO semantic edges, merges, or guessed revision ancestry. Re-running the same snapshot produces identical staging output. A changed snapshot is a new plan, not permission to overwrite previously committed rows. The 40k-character staging guard is conservative and not a measured Claude limit; over-limit content stops before upload, retaining the source.
4. Through the actual Sheets connector create one new staging workbook in the SAME selected folder, with the five schema tabs. Write complete literal payload rows using genuine append, verify exact values, then append and verify commit manifests. Reuse staging IDs on resume. Read imported workbook contents against the staging file if using XLSX import; conversion can alter types or timestamps. Do not activate an unverified import. Directory positions are tentative until actual native row locations are verified. Do not copy a precomputed row location blindly after appends or sorting.
5. Map each original source to its imported node/event and verify exact meaningful text, attribution, source IDs and reasons. For baseline/addendum/mirror/replacement relationships, inspect explicit source links and resolve the original logical identities; do not treat each imported source as a new person. Preserve distinct contributions. Append supported graph edges only when both endpoints are verified nodes and the relation was explicitly supported by the source; History links remain source/event references. Unknown links remain unresolved text, not invented edges.
6. The utility output is **staged-unverified**, not automatically equivalent current memory. Where Docs baseline plus addenda form one current topic/person, prepare full consolidated node versions only after checking all contributions and preserving original imports and History. Reference the exact source nodes/events and document the mapping. Do not invent predecessor ancestry from timestamps or silently flatten disagreement. All logical People identities, recognition mappings, Self choices and original reasons must have unambiguous mappings before activation. Audit current and historical source-fidelity separately.
7. Re-read source revisions/full content immediately before final verification. Reconcile changes since export by another staged operation; if the source continues changing, leave it on Docs and report the incomplete handoff. There is no atomic transaction between config, Docs and Sheets. Ask collaborators to pause writes during the final handoff when needed; this is coordination, not a software lock. Verify destination full rows, counts, IDs, manifests, references, immutable prior states and fresh-Claude recall. Missing records, over-limit cells, incompatible tools, unresolved identity mappings or lost source coverage block activation, not unrelated Docs learning.
8. Only after the requested review and explicit authorization to activate, update the existing config representation with `storage_format:sheets-graph-v1`, `cortex_schema_version:1` and the verified spreadsheet ID. Preserve the plugin UUID, schema_version 1, label and folder ID. Use a real precondition if exposed; otherwise coordinate the single administrative switch, reread and verify it, disclosing that concurrent config edits are not protected. Never create competing description/body pointers. Keep the old configuration and all source Docs untouched as fallback.

Migration does not weaken learning or repair experimental user memories. If partially staged, keep Docs authoritative and continue normal learning there. Resume by exact IDs and verified payloads, never by re-appending the whole export blindly. Do not claim a successful migration because an XLSX imported or a row count matched. [Rollback](ROLLBACK.md) covers graph-only changes after activation.
