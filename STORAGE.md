# Readable Google Docs memory protocol — 0.2.6

Google Drive handles files, scope and config; Google Docs handles authoritative memory bodies. The user reports successful actual-Claude creation, reading, editing an existing document and read-back. Revision preconditions were not confirmed. Inspect actual tools and use the strongest exposed behavior; never invent an API parameter. No new backend, MCP, graph or server is introduced.

## Representation and authority

Keep Self, People, Knowledge, History and existing file identities. New memory docs have a meaningful title and readable headings: Remembered information, Reasons/context, Who said or concluded what, Evidence, Uncertainty. A small readable footer states “Yori memory format: 2”, record kind and verified source links. This is not opaque JSON. Use actual Docs heading/paragraph styles when the connector exposes them; otherwise keep clear plain-text headings and spacing rather than assuming Markdown will render. Verify readable text and intended structure, never claiming a visual preview was inspected unless it was. Full bodies are authoritative after verified format-2 creation/migration. Description metadata holds optional structural hints or preserved legacy source only. [Migration](MIGRATION.md) resolves mixed versions safely; never overwrite divergent body content from metadata.

History holds committed contribution, prior-state, correction and migration-evidence Docs. Create complete content, verify actual body/parents, then never edit that committed document, even to fix references or technical details. A complete but unverified write may already be committed: uncertain is not permission to rewrite. Initialization of a newly created empty Doc is part of creation only when its exact ID/ownership/empty body/final parent are verified; never commandeer an unknown empty file. With no required-revision guard, initializing one's just-created empty file is permitted with immediate before/after body checks, but an external edit race cannot be excluded. Use atomic create-with-body when supported at the final intended parent; otherwise create empty, place and verify it first, then initialize. Do not write a complete History body at root and later move it as if still uncommitted. Any unexpected nonempty content stops initialization.

Use provider-generated Drive document IDs as canonical identities. A genuine generator exposed by the host may supply a retry token; never handcraft random-looking reference codes. A contribution's returned ID is operation_id for dependent docs; do not backfill it into committed History. Verify every reference's exact ID, kind, scope and body, reusing fresh receipts. Legacy IDs remain valid. Corrections are new linked documents, not silent edits of old evidence. See [integrity](references/memory-integrity.md).

## Required order for current-memory changes

1. Resolve scope/capabilities and read the current full body, title, relevant tabs, returned revision (if exposed), parents and relevant pending addenda. Reuse a complete valid same-turn read; metadata etag alone does not protect Docs contents.
2. Create and read back the immutable contribution describing the new evidence with claim-level provenance. Independent initial target reading may overlap this creation, if supported. Do not create another contribution on a retry with a known receipt.
3. Preserve the exact previous meaningful body and title, source ID, observed revision when available, uncertainty and references in new History prior-state Docs. Preserve text from every relevant section/tab, not just a flattened truncated excerpt. Number and verify all parts if necessary. Formatting need not be pixel-identical, but meaningful text, structure, reasons and links must survive. A snapshot is an observed state, not proof a later edit committed. Any snapshot verification failure blocks a destructive current edit.
4. With a real Docs required-revision precondition, validate references, recheck parent scope, apply the minimal body edit against that observed revision, then read back the full affected meaning and body revision/parents. On rejection, reread winner, snapshot that version, reconcile both contributions and retry at most twice. Do not treat collaborative/target-revision transformation as strict compare-and-swap unless the actual connector semantics establish it; otherwise use fallback.
5. Without a strict revision precondition, keep the current Doc unchanged. Create a complete immutable readable addendum in the same Self/People/Knowledge folder, titled “Update — <topic>”, containing the proposed change/current understanding, reasons, exact “Updates” baseline ID, verified contribution and prior-state IDs, observed revision/body context and uncertainties. Verify body/placement. This safely persists learning even without optional concurrency features. It may require reading more documents; it does not guarantee automatic consolidation. Never silently label a concurrent addendum as superseded solely by date.
6. Recall reads current baseline plus relevant verified addenda and pending History contributions. A revision-guarded later consolidation may update the baseline with references to included addenda, after snapshotting its current state. Addenda/History stay intact; inclusion references prevent duplicate interpretation. Without a guard, they remain readable supporting documents, not a fake lock or an unguarded summary rewrite.

Every actual current-body edit, however minor, uses this ordering. No-op recall needs no write. Unexpected source moves/access failures stop dependent writes. Parent checks are not atomic with Docs revision checks. Partial failures preserve contributions/snapshots, report the real state and do not roll back someone else's winner. If a create response is lost, recover by known ID or genuine retry token with unique verified evidence; uncertain identity is not a license to create duplicate documents.

## Practical limits

Append-only History is an instruction, not server-enforced immutability against outside editors. No multi-file transaction, exactly-once guarantee or parent isolation is claimed. Missing revision guards do not block setup, read-only access or new learning; addenda avoid unguarded replacement. Missing Docs read/write or scope verification blocks only dependent operations and must be explained plainly. Missing legacy description access blocks that conversion, not new Docs learning in verified scope. Do not replace these safeguards with a latency target.
