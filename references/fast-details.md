# FAST retrieval and exceptional cases

## Recovery and concurrency

Keep the original operation and exact full intended rows after timeouts, errors and uncertain responses. Retrieve all occurrences of that op with complete coverage. If complete and matching, no write. If incomplete and observed parts match, append only missing original rows using the SAME op/part/total; verify. A partial window cannot prove absence. If the original intent was lost, do not invent missing content or lower total; leave pending and explain. Conflicting payloads stop dependent writes; preserve evidence and unrelated safe work. A whole-call retry can make physical duplicates; logical deduplication is required. A later conflicting duplicate can invalidate earlier visibility. No exactly-once or serializable transaction claim.

Two users revising A produce B→A and C→A. Preserve both heads and each author's reasons. A deliberate reconciliation names B,C; later unseen D→A still remains a head. Reject missing/cyclic/cross-entity parents and dangling endpoints. User edits/deletions are outside the append-only writer protocol. Without hashes/signatures, later well-formed human edits are not always detectable. No ACL immutability or tamper-proof claim.

ID limitation: model-produced tokens are not verified random/unique identifiers. Detect observed collisions through exact payload and complete part checks; never silently replace. A collision between different operations with indistinguishable or complementary partial rows cannot always be detected. If guaranteed uniqueness is required, an actual trusted ID signal/generator is a prerequisite; report its absence and do not present the fallback as guaranteed safe. No new service or Bash is introduced to manufacture that guarantee. Source-message identity and by/source context must not be invented. Tests with distinct IDs establish branch preservation, not collision impossibility.

## Efficient current retrieval

Prefer actually exposed exact ID/topic/relationship search with complete bounds/pagination; fetch full rows plus all sibling parts of matching operations and necessary ancestors. Search by topic alone can miss a renamed/revised topic: resolve entity IDs and all heads before answering. A returned match isn't a complete current view. Related History/old versions never supersede current nodes by proximity.

When only range reads exist: once per fresh chat, read bounded index columns A:I to the verified current end, build in-chat maps of entities, operations, topic keys and endpoint relationships, and fetch relevant full rows J:N and their siblings. Do not dump all memory text for each question. Before subsequent current claims, refresh newly appended rows from the last fully covered boundary to a newly verified end; update maps and reload affected operations. Recheck previous incomplete operations. A receipt for your own append is not coverage of concurrent writers' intervening rows. Gaps/early blank rows aren't proof of end. Never skip unseen tail rows or pending siblings by advancing a watermark blindly. Reopen/reset after scope change, external reordering/deletion or invalid hints.

Warm questions use cached maps plus the tail and targeted full rows, normally one hop; increase only when relevant. The cold index is O(N), and tail refresh is O(new rows), not an indexed database guarantee. Without exact server search or a retained chat cache, a fresh chat requires a scan; don't claim sublinear cold reads. Local developer benchmarks are not remote timing measurements. If partial coverage or tool limits prevent resolution, say so rather than invent recall.

## Existing Cortex compatibility

Installation changes no pointer or data. Existing five-tab graphs keep the legacy reader and commit verification. FAST can additionally read a verified `active_cortex.legacy_graph_spreadsheet_id`; this is a read-only source, possibly the same workbook containing the old tabs. Union legacy node/edge revisions and History with FAST rows by stable IDs. New revisions may reference original legacy entity/revision IDs. Preserve all source records, reasons, unknowns and conflicting branches. Refresh relevant legacy state too while old clients can write; a FAST tail alone is insufficient.

Enable a FAST destination for an existing Cortex only after disposable acceptance and an explicit switch request. Retain exact config backup and legacy ID, create/verify Memory without altering old tabs, audit old current heads/History and the dual reader, then change/verify the pointer using the existing config convention. Coordinate writers for the pointer switch; no CAS is assumed. No bulk copying or deletion is needed. Old Docs installations remain on their reader; no automatic Docs migration. Downgrading after FAST learning cannot discard that learning: keep the new reader/config until an explicitly verified export/reconciliation is complete. A source access failure is a recall gap, never permission to initialize a new Cortex.
