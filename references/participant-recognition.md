# Participant recognition — natural continuity without false authentication

Apply before person-specific recall or attribution in each fresh chat, using the exact selected Cortex. This is conversational recognition, not an access-control system. Google permissions govern file access; these instructions govern what Yori attributes and volunteers. No new auth server, config format or participant database.

## Three different identities

- Claude account: use a stable ID only if the actual host supplies a trusted current-user field or exposed identity tool. Skill name, session/conversation ID, workspace ID and a value written in a document are not the Claude user ID. Never invent such an API or assume it exists.
- Connected Google account: an actual current-account profile tool may return a provider ID and/or email. It authenticates the connected account at this tool boundary, not the human at the keyboard. A document owner, editor, permission entry, display name or source link is not a current-account identity signal. Google and Claude accounts may differ; never merge them by matching email text alone.
- Cortex participant: a People record with evidence of direct participation. Other people merely mentioned in conversation are not automatically participants. Multiple representations/addenda of one logical People source are one person, not separate participants.

Inspect current tool definitions through actual discovery. If a trusted current-account profile action is exposed, call at most once per fresh chat when useful and reuse the result; never invoke the Codex-specific tool name just because developer testing found it elsewhere. Prefer provider subject/account ID with documented or clearly scoped semantics. Record exactly which provider, tool/field, account namespace and value were observed. Do not assume an opaque ID is portable across connectors or organizations without evidence. If only email is exposed, treat it as a weaker current account address, not immutable person identity; do not guess aliases, strip dots/tags or equate addresses across providers. A display name alone is not a key. No profile tool or a failed lookup is not a setup/recognition blocker.

The builder observed a Codex Google Drive profile ID/email/name, not Claude's interface. Availability and cross-chat stability in Claude remain to be checked. Never promote that development observation into a guaranteed Claude capability.

## Persist a grounded mapping, not a guessed one

Keep an optional readable Recognition section in the appropriate EXISTING People Doc or a verified addendum referencing that same logical People ID. See [template](../templates/participant-recognition.md). Follow STORAGE.md: append an attributed History contribution, snapshot/guard a current edit when supported, otherwise use a body addendum; read back and verify. Do not create a duplicate person or a new registry just to store a key. No write merely for a successful returning greeting.

A mapping needs BOTH an actual current-account signal and evidence linking that account's present speaker to the correct People record: for example, explicit self-identification with sufficient context to resolve that existing participant, or an already verified mapping with no contradiction. Names alone, sole-participant defaults and shared access cannot establish a persistent account binding. If matching an existing person is ambiguous, retain unresolved evidence or ask only when the pending attribution needs it. Do not interrupt an ordinary greeting solely to enroll a mapping.

Persist provider/field/namespace, observed ID (email only if needed), target logical People ID, linkage basis and evidence, known time/source, and whether the key is known shared or revoked. Minimize account data; never store credentials/tokens or copy identity keys into ordinary responses. These docs inherit folder visibility. The person link remains self-reported/contextual unless stronger actual evidence exists; a Google account association is not verified human identity. Keep conflicting/shared-key bindings as ambiguous instead of taking the newest one. Corrections/revocations append History and obey current-record revision rules. Never silently rebind an account because another speaker used the same connection.

Legacy People records without a Recognition section still work. Preserve them; derive participation only from existing direct-conversation evidence. Do not bulk enroll or repair old records on upgrade.

## Resolve this chat

Use this order, retaining the basis in turn context:

1. Explicit current-chat self-identification/correction takes precedence over a greeting default. A guest saying “I'm someone else” invalidates the prior speaker assumption immediately; it does not revoke/rebind the owner's account mapping automatically. A supplied name supports a natural greeting as self-reported, but does not prove it matches a same-named saved person. Resolve only consequential ambiguity.
2. If an actual current-account signal has one active, scoped, evidenced mapping to a People record and no sharing/conflict/contradiction, reuse that record naturally. Basis: authenticated account signal plus recorded person association, not authenticated human. Do not ask “Is this <name>?” every chat. If the provider ID matches while email changes, retain the ID match and do not create another person. A different provider/key does not match merely because the text or email is similar.
3. Without a usable authenticated mapping, if scoped evidence establishes ONE known participant and no contrary evidence of a guest, other active participant, shared key or conflicting account association, use that participant as a CONVERSATIONAL DEFAULT. Greet naturally, e.g. “Hi, Deepak.” Do not add an identity caveat, question or repeated folder-sharing explanation to a routine greeting. Missing/failed profile lookup does not defeat this default. Do not claim “I verified it's you,” persist an account binding from it, or record inference as authenticated fact. A folder shared with others is neither proof of another active speaker nor proof of the current speaker; actual participant evidence controls the default.
4. Multiple known participants, explicit shared-account use, incomplete participant coverage, conflicting bindings or a known-new/different account inconsistent with an existing mapping mean unresolved identity. A generic greeting or identity-independent task can proceed without any question. Ask one brief question only before a person-specific task, consequential attribution or requested personal recall requires resolving who is speaking. Do not list private facts or everyone else's names as answer choices.

Count logical participants, not files or every named person. Reuse scoped People/History evidence already loaded. If listing/pagination is incomplete, do not call it a sole-participant Cortex. Do not perform a broad personal-history scan merely to greet. No account-email question is required just to use the personal default.

## Disclosure and learning

A natural name greeting does not authorize reciting personal conversational history. Do not volunteer person-specific memories while saying you do not know who is speaking. When identity is unresolved, answer general/shared topics and withhold personal-history references until relevant identity is established. Do not say “Is this Deepak? Last time you told me ...”. Folder access is not proof of speaker identity.

The sole-participant default supports ordinary conversational continuity and routine low-risk learning in that personal context. Retain the attribution basis as “sole known participant assumed,” not explicit self-identification. If a task involves sensitive personal history or an irreversible/consequential attribution, clarify only then. A current-chat correction stops attaching new contributions to the old participant; preserve prior History and append correction rather than silently rewriting it. Explicit identity-dependent requests may be answered using the available contextual basis without falsely calling it authentication.

Automatic selective learning continues even when identity is unresolved: preserve worthwhile content as an unattributed/unknown-speaker contribution or shared knowledge, with uncertainty, rather than dropping it or assigning it to someone else. No duplicate People record just for an unknown greeting. Yori's Self retrieval and independent learning do not wait for participant identification. Do not repeat the sharing explanation on routine reconnection; mention it only when the audience changes or it matters to the task.
