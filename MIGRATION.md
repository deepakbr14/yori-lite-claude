# Safe migration to readable Docs — format 2

For `sheets-graph-v1`, use [graph protocol](references/graph-cortex.md) and [Docs-to-Sheets migration](GRAPH_MIGRATION.md). The Docs-specific mechanics below remain unchanged for legacy installations only.

Installing 0.2.6 alone changes no Drive data. Preserve the fixed plugin UUID, config filename, selected Cortex ID, Self/People/Knowledge/History and all original sources. Do not create a new Cortex because an old body is blank. Never migrate original personal Yori. Migration requires authorization for the selected Lite Cortex and actual Drive description reads plus Docs body create/read/edit capability. User-tested Docs support establishes the design; unavailable source fields block affected conversions, not the whole installation.

## Version and authority

Config schema_version remains 1 and accepts optional storage_format: metadata-v1, mixed-v1-v2, docs-v2. New installations use docs-v2. Missing field means legacy/undetermined; inspect actual representations. Per-document visible “Yori memory format: 2” identifies the body format, not proof of a completed migration. A Cortex with partially converted sources is effectively mixed regardless of an optimistic config marker. Do not set docs-v2 for a legacy Cortex until every semantic source is accounted for and verified. Keep existing config pointers unchanged; update an optional format field only with the actual safe config editing capability. If that is unavailable, retain the old config and derive mixed authority from verified per-document receipts. Never block new Docs learning merely because a config format hint cannot be updated.

For each legacy identity, use the verified format-2 body plus its subsequent contributions/addenda only after conversion proof. Retained description is archival source, not a competing latest memory. Unconverted descriptions remain authoritative legacy evidence and are read-only in 0.2.6. Conflicting or unverified bodies are not silently trusted or overwritten. A legacy source modified after migration is new conflicting evidence; flag/reconcile through new contributions instead of blindly recopying it over later Docs learning.

## Resumable per-source conversion

1. Enumerate scoped files with full pagination and verify IDs/parents/type. Exclude administrative README/setup probes from semantic migration, leaving them untouched. Read the complete source description and source revision/etag if exposed; a missing field is unknown, not empty. Also inspect actual body and all relevant tabs. Preserve legacy 0.1 nonempty bodies as existing evidence; do not blank or convert them merely because descriptions are empty.
2. Before creating anything, search/list candidate body documents and migration receipts within the same Cortex by source ID and verify their contents. Source ID, exact captured description, source revision when available, destination ID and format form the resume identity. Never depend on filename uniqueness or unverified description indexing. If complete enumeration is impossible, do not claim no prior conversion exists. Existing unique verified match is reused, not recreated; multiple contradictory candidates stop that source for review.
3. Preserve a readable immutable migration-evidence document in History with the exact original description text, original source ID/title/type and observed revision or “unknown.” Distinguish legacy assertions from newly verified facts; don't fix old pronouns or turn old inferences into quotes. Verify its body and parent. On interrupted recovery reuse that exact verified receipt; uncertain create identity is not permission to repeat blindly.
4. Prefer keeping the same native Google Doc file ID when its body is verifiably empty and an actual required-revision guard can protect filling it. Use a guarded body initialization against the observed empty Docs revision; the legacy description is unchanged. If it has meaningful nonmatching content, preserve it and mark a conflict, never overwrite. If it is not a native Doc or no guard can safely protect the old file, create a separate readable migration mirror in the same Self/People/Knowledge/History folder. Keep the original source file ID as the logical memory/person identity and put “Legacy source” with that exact ID in the body. The mirror ID is its physical representation, not a duplicate person. No source deletion/rename or misleading claim that physical IDs stayed equal.
5. Render clear headings and paragraphs preserving all meaning, reasons, authorship distinctions, dates, references and uncertainty. Include a readable “Migration” section naming legacy source ID, migration-evidence ID and format 2. Do not dump opaque JSON; the evidence document preserves exact source text for audit. For an ambiguous legacy claim, label it as legacy/unverified rather than inventing attribution. Committed legacy History is materialized without semantic correction; its source description remains immutable.
6. Read back the complete destination body, verify expected meaning and references, actual parent, source identity and lack of truncation. Reread source metadata and compare exact description/revision with the captured version. A changed source leaves conversion pending/conflicting; retain both, never silently select the old snapshot as current. Verification is optimistic, not a cross-connector transaction.
7. Create and verify an immutable completion receipt in History linking the source, captured evidence and destination. Only then treat the converted body as authoritative for this source. Receipt creation may fail independently: retain the candidate and resume by validation, not duplicate copying. A complete nonempty destination/receipt is not a mutable draft. Never edit a committed History body to add a self-ID or corrected technical reference.
8. Update optional Cortex storage_format from legacy to mixed and finally docs-v2 only when supported and all scoped semantic sources are verified. New files added concurrently or unresolved sources mean mixed. Final detection cannot guarantee global atomicity: per-record verified authority takes precedence over this hint.

There is no exactly-once multi-file transaction. Resume with captured IDs and exact-source evidence; concurrent migration can create duplicate candidates. Detect/report them and stop ambiguous authority rather than deleting one or creating another. Don't mark the entire Cortex migrated after a partial pass. Preserve the complete legacy source indefinitely unless the user later explicitly authorizes a separate cleanup. No bulk cleanup or silent dataset repair is part of this release.

## New learning during a mixed migration

Do not wait for the whole Cortex. Read relevant legacy plus verified Docs evidence. New contributions go to readable History bodies. If the affected current source is unconverted or ambiguous, preserve new learning as a readable addendum referencing its stable source ID, without modifying the legacy source. Recall includes those addenda with appropriate uncertainty. On conversion, keep their references and do not overwrite them with a stale source. Person matching uses the logical source identity across representations.
